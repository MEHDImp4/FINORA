# Quick Task 260914-mh1: True Download Resume After Process Death

**Date:** 2026-09-14
**Slug:** true-download-resume-after-process-death

## Problem

FINORA persists download *metadata* and restores a paused-looking list after an app kill, but the
network transfer itself cannot be reconstructed:

1. `executeDownload()` calls `createDownloadResumable(url, fileUri, options, callback)` with **no
   `resumeData`** argument, so nothing ever continues from a byte offset.
2. Persistence strips the auth token from the URL and restore drops `options.headers`, so a
   restored download has neither token nor headers and would 401 if it ever ran.
3. `activeTasks` is in-memory only, so `resumeAsync()` is unreachable after a restart.
4. Queue order is transient; every state transition writes to AsyncStorage on a 200 ms timer,
   including every progress tick.

The documented behaviour is therefore cosmetic, not functional.

## Verified native facts (established from the installed expo-file-system 57.x sources)

Android — `node_modules/expo-file-system/android/src/main/java/expo/modules/filesystem/legacy/FileSystemLegacyModule.kt`

- `:661-663` — `resumeData?.let { requestBuilder.addHeader("Range", "bytes=$it-") }`
- `:632-633` — progress report already adds the offset to both written and expected byte counts
- `:698` — `downloadResumablePauseAsync` returns `resumeData = file.length().toString()`
- **`resumeData` on Android is literally the byte offset.** It can be synthesized by us from the
  partial file size — `pauseAsync()` is not required. This is what makes a hard-kill resume possible.
- `:926` — `FileOutputStream(file, isResume)` opens the destination in **append** mode on resume.
  → if the server answers `200` (ignores `Range`), the whole body is appended to the partial file.
  This is silent corruption and MUST be detected in JS via the response status.

iOS — `node_modules/expo-file-system/ios/Legacy/FileSystemLegacyModule.swift`

- `:277-278, :306` — `resumeData` is a base64 `NSURLSession` resume blob from
  `cancelByProducingResumeData()`. That blob embeds the original request **including our
  `Authorization` / `X-Emby-Token` headers**.
- Therefore iOS resume data must never be persisted (it is a credential). Synthesized-offset resume
  is platform-gated to Android; on iOS a partial file with no in-memory task restarts from zero and
  this limitation is documented rather than hidden.

## Task 2 — DownloadManager resume engine

**files**
- `src/features/offline/downloadManager.ts`
- `src/app/_layout.tsx`

**action**

1. **`restorePersistedDownloads()` — file-state reconciliation** (mission cases A–D):
   - Case D: file exists and `totalBytes > 0 && fileSize >= totalBytes` → persist the offline record
     via `offlineStorageService.saveOfflineMedia(...)` and drop it from the active map as
     `completed`. Never resume an already-complete file.
   - Case B: metadata present but no file → reset `bytesDownloaded`/`resumeOffset` to 0 (never show a
     fake percentage) and put the item back in `queued` for a clean restart.
   - Case A: file present and smaller than `totalBytes` → set `resumeOffset = fileSize` and
     `bytesDownloaded = max(entry.bytesDownloaded, fileSize)`.
   - Case C: partial file with no metadata is left to the existing
     `offlineStorageService.cleanupOrphanDiskFiles()` — do not duplicate orphan logic here.
   - Restore `downloadConfigs` **including `options`** (currently dropped) plus `quality`,
     `serverId`, `userId`.

2. **`initialize()`** (`src/app/_layout.tsx` switches to it):
   - `await restorePersistedDownloads()` → resolve `getDownloadAuthContext()` once → validate each
     item's `serverId`/`userId`/normalized `serverUrl` against the context.
   - Status routing: persisted `downloading` → auto-resume (requeue, in original order); persisted
     `queued` → requeue in original order; persisted `paused` → **stays paused**, never auto-starts;
     persisted `failed` → stays failed.
   - Mismatched server/user, or no auth context → status `paused` carrying a controlled reason
     (`AUTH_REQUIRED` / account mismatch), partial file and metadata preserved, removed from queue.
   - Wi-Fi-only gate: when the pref is on and we are not on Wi-Fi, restored items stay `queued`
     instead of being started (so they are not failed by the cellular gate).
   - Restore queue order from `@finora_download_order`, then call `processQueue()` so the existing
     `MAX_CONCURRENT_DOWNLOADS = 3` cap is enforced by the existing scheduler.
   - Idempotent (guard with an `initialized` flag).

3. **Authenticated request rebuild**: in `executeDownload()`, when the item has `quality` and an auth
   context is available, rebuild
   `buildDownloadUrl(ctx.serverUrl, itemId, ctx.accessToken, quality)` +
   `getDownloadHeaders(ctx.accessToken)`. Reuse the existing `downloadQuality.ts` builders — do not
   add a second URL builder. Never log the token or a token-bearing URL.

4. **Real byte-offset resume**:
   - Resolve the real partial size with `FileSystem.getInfoAsync(localPath)`.
   - Android, `0 < partialSize < totalBytes` → pass `resumeData = String(partialSize)` as the 5th
     argument to `createDownloadResumable` and record the offset.
   - iOS → do not synthesize a numeric offset (the native side base64-decodes it and would reject or
     restart); if a partial file exists with no in-memory task, delete it and restart from zero.
   - Keep the existing in-process `pauseAsync()` / `resumeAsync()` path working unchanged.

5. **Range guards** (after `downloadAsync()` resolves, when `resumeOffset > 0`):
   - `206` → genuine resume; continue.
   - `200` → the body was appended to the partial file → **corrupt**: delete the file, reset
     `bytesDownloaded`/`resumeOffset` to 0, restart from zero exactly once, and never mark it
     `completed`.
   - `416` → verify the file against `totalBytes`; complete it only if it matches, otherwise restart
     from zero.
   - A corrupt/concatenated result can never reach `completed`.

6. **Bounded 401/403 recovery**: on auth failure during a resume, refresh the auth context, rebuild
   the task and retry **at most once** (per-item flag). If it fails again → recoverable failure state
   with the partial file preserved. Change the current `status >= 400` branch so it no longer deletes
   the partial file (network and auth failures must keep it).

7. **Completion integrity**: before `completeDownload`, verify the file exists and, when
   `totalBytes > 0`, that the real on-disk size is consistent with `totalBytes`. Guard the
   unknown-length case (Jellyfin can report `-1`). On mismatch → recoverable failure, file kept, not
   completed.

8. **Persistence cadence**: keep immediate persistence for every state transition (queue add/remove,
   pause, resume, cancel, restore). Throttle the high-frequency progress path in `updateProgress` to
   roughly every 3 s or a ≥1 % delta. Add `flushPersist()` (clears the debounce timer, awaits
   `persistQueue()`) and wire an `AppState` `background`/`inactive` listener to it. AppState is a
   best-effort addition, not the primary mechanism.

9. **Logging**: only `downloadId`/`itemId`/`bytesDownloaded`/`totalBytes`/`status`/`reason` via the
   existing `logger` (which already scrubs Authorization / X-Emby-Token).

**verify**
- `npm run typecheck` passes.
- `npm test` passes.
- Manual code trace: with `resumeData = "3100000000"` recorded, `createDownloadResumable` is called
  with that 5th argument; a mocked `status: 200` result triggers delete + restart, never `completed`.

**done**
- A restored download rebuilds an authenticated, cancellable, resumable task from metadata +
  SecureStore session + the existing partial file.
- No path can mark a corrupt file `completed`.
